# ADR-004: Асинхронная доставка уведомлений

**Статус:** Принято

---

## Контекст

Система должна автоматически оповещать пользователей о событиях: назначение задачи, упоминание в комментарии, смена статуса, приближение дедлайна. При этом уведомления могут доставляться сразу нескольким получателям, а часть из них — по email, что требует обращения к внешнему SMTP-серверу.

Если обрабатывать уведомления прямо в теле HTTP-запроса (синхронно), пользователь будет ждать завершения всех побочных операций — это замедляет ответ API и делает его хрупким при сбоях внешних сервисов.

---

## Решение

Мы будем обрабатывать уведомления **асинхронно** через очередь задач на базе **Celery + Redis**.

Каждое бизнес-событие (назначение, комментарий, смена статуса) помещает задачу в очередь. Воркер Celery обрабатывает её независимо от HTTP-запроса: сохраняет запись в базе данных и, если пользователь подписан на email-канал, отправляет письмо.

---

## Последствия

**Положительные:**
- API отвечает немедленно — пользователь не ждёт доставки уведомлений
- Сбой email-сервера не ломает основные операции с задачами
- Можно добавлять новые каналы доставки (push, Slack) без изменения бизнес-логики
- Возможность повтора при временных сбоях (retry policy)

**Отрицательные:**
- Появляется новая инфраструктурная зависимость (Redis, Celery-воркер)
- Уведомления доставляются с небольшой задержкой (eventual delivery), а не мгновенно
- Локальное окружение разработки усложняется: нужно поднимать воркер вместе с сервером
