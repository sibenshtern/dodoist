# ADR-005: Верификация email и сброс пароля

**Статус:** Принято

---

## Контекст

При регистрации нужно убедиться, что пользователь владеет указанным email-адресом. Также необходим механизм восстановления доступа при утере пароля.

Типичные подходы к передаче токенов верификации и сброса:

| Подход | Описание |
|---|---|
| Токен в теле запроса | `POST /auth/verify-email` с `{"token": "..."}` |
| Токен в URL-параметре | Ссылка вида `/verify?token=...` в письме, GET-редирект |
| Токен в HTTP-заголовке | `POST /auth/verify-email` с заголовком `X-Verification-Token` |

---

## Решение

Мы будем передавать токены верификации и сброса пароля **в HTTP-заголовках** (не в теле запроса и не в URL). Письмо содержит ссылку на страницу фронтенда, которая извлекает токен из URL-параметра только для отображения, а к API обращается уже через заголовок.

Это соответствует уже принятому в проекте принципу: пароли тоже передаются в заголовках (`X-Password`, `X-Current-Password`), а не в теле запроса.

---

## Последствия

**Положительные:**
- Токены не попадают в логи сервера, трейсы прокси и историю браузера
- Единообразие с остальными auth-операциями проекта
- URL ссылок в письмах короткие и не содержат конфиденциальных данных

**Отрицательные:**
- Нестандартный подход — разработчики, привыкшие к стандартному OAuth/OpenID, могут удивиться
- Фронтенд должен извлекать токен из URL и сразу передавать в API, а не передавать ссылку напрямую
- Сложнее тестировать вручную через браузер без специального клиента (Postman, curl)
