# ADR-007: Предагрегация данных для аналитики

**Статус:** Принято

---

## Контекст

Продукт должен показывать burndown-диаграммы, velocity по спринтам и метрики по участникам. Для этого нужно знать состояние задач в каждый день спринта — историческую информацию, которую нельзя получить из текущего снимка базы данных.

Рассматривались два подхода:

| Подход | Описание |
|---|---|
| Вычисление в реальном времени | Агрегировать данные из `activity_log` при каждом запросе дашборда |
| Ежедневные снимки | Хранить предагрегированные счётчики в отдельных таблицах |

---

## Решение

Мы будем использовать **ежедневные снимки состояния**: фоновая задача (Celery beat) каждую ночь обходит активные проекты и записывает агрегированные показатели (количество задач, story points, просроченные и завершённые) в специальные таблицы `task_snapshots` и `user_metrics`.

Дашборды читают данные из этих таблиц напрямую — без сложных агрегатных запросов к основным таблицам.

---

## Последствия

**Положительные:**
- Запросы дашборда выполняются быстро — данные уже посчитаны
- Нагрузка на базу данных равномерна: тяжёлая агрегация происходит ночью, а не в пиковое время
- Исторические данные сохраняются даже после удаления задач

**Отрицательные:**
- Данные актуальны только на начало текущего дня (задержка до 24 часов)
- Показатель «сейчас» для summary-дашборда считается в реальном времени отдельным запросом
- При ошибке ночного задания данные за день могут отсутствовать — нужен механизм дозаполнения (backfill)
